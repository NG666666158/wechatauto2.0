# Windows EXE 打包收口路线图

## 目标

把当前开发态项目收口成面向小白用户的一键启动 Windows 客户端。客户端应表现为一个普通桌面软件：用户打开 exe 后，在首页点击启动本地服务，随后按顺序完成微信环境检测、自动回复启动和运行状态查看。

第一版不追求把所有高级能力都展示出来，优先保证能稳定启动、能导入知识库、能记录消息、能按身份和知识生成回复、能把中高风险内容交给人工处理。

## 当前架构判断

当前项目是：

```text
Electron 客户端壳
  -> 加载 Next.js 前端页面
  -> 调用本地 FastAPI 后端
  -> 后端控制微信运行时、知识库、身份、设置和日志
```

这个方向适合打包成桌面应用，但现在仍偏开发态：

- Electron 默认加载 `http://127.0.0.1:3000`。
- 后端启动依赖本机 `py -3 -m uvicorn ...`。
- 前端依赖 Next.js dev/start 服务。
- 数据目录仍在仓库内的 `wechat_ai/data/`。
- 打包脚本、安装包配置、干净用户数据目录和首次启动体验尚未形成闭环。

## 第一版建议保留的页面和能力

### 首页

- 本地服务状态。
- 微信连接状态。
- 自动回复状态。
- 今日收到消息数。
- 今日回复用户数/回复次数。
- 待处理事项数量。
- 快捷操作：
  - 启动本地服务
  - 检测微信环境
  - 确认开始自动回复
  - 刷新运行状态

### 消息

- 只作为聊天记录和 AI 回复记录页面。
- 不在此页面发送消息。
- 保留会话列表、聊天记录、记录摘要。
- 删除或隐藏发送输入框、不可点击菜单、测试数据和内部 ID。

### 待处理

- 只展示中高风险待人工接入内容。
- 不展示低风险普通记录。
- 删除重复的风险概览大块。
- 操作重点是人工接管、暂停会话、查看风险原因。

### 客户

- 保留客户身份。
- 保留全局自我身份。
- 明确哪些字段会提交给模型作为身份依据：
  - 客户名称
  - 标签
  - 用户身份
  - 来源渠道
  - 全局自我身份
- 客户 ID、最近联系等系统字段只用于记录和排序，不作为主要回复依据。

### 知识库

- 保留文件拖拽入库。
- 保留知识库状态、最近构建日期、检索和最近任务。
- 检索结果使用悬浮页展示。
- 第一版重点是跑通入库和检索，不展示复杂可信门禁。

### 设置

- 保留模型配置。
- 保留自动回复开关。
- 保留工作时间。
- 保留安全词管理。
- 保留微信路径和开机自启。
- 所有保存结果使用 1-2 秒悬浮提示，不独立占用页面区域。

## 打包前必须开发的内容

### 1. 正式打包链路

需要引入 `electron-builder` 或同类工具，生成 Windows 安装包或单 exe，并配置：

- 应用名称。
- 应用图标。
- 版本号。
- 安装目录。
- 自动创建桌面快捷方式。
- 打包文件白名单。
- 用户数据目录。

### 2. 后端独立打包

当前后端依赖源码目录和用户电脑已有 Python，不适合小白使用。

第一版推荐：

```text
PyInstaller -> wechat-ai-backend.exe
Electron -> 启动 wechat-ai-backend.exe
后端 -> 监听 127.0.0.1:8765
Electron 退出 -> 停止后端
```

需要验证：

- FastAPI 能从 exe 正常启动。
- pywinauto/pywin32/pyautogui 能随 exe 正常工作。
- docx/pdf/图片 OCR 依赖能被正确打包。
- 后端日志写入用户数据目录。

### 3. 前端生产加载方式

当前前端是 Next dev server，不能要求用户启动 `npm run dev`。

需要改成：

- 打包前执行 Next 生产构建。
- Electron 加载生产前端产物。
- 不依赖开发端口 `3000`。
- 本地 API 地址仍指向 `127.0.0.1:8765/api/v1`。

可选方案：

- 方案 A：Next static export 后由 Electron 直接加载本地文件。
- 方案 B：Electron 内置一个轻量静态文件服务。
- 方案 C：保留 Next standalone 生产服务，由 Electron 拉起。

第一版推荐 B 或 C，优先少改业务代码。

### 4. 一键启动服务

首页的“启动本地服务”应做成傻瓜入口：

1. 检查后端是否已运行。
2. 未运行则拉起后端 exe。
3. 轮询 `/api/v1/ping`。
4. 成功后更新首页状态。
5. 失败时显示明确原因和下一步建议。

用户不应看到 uvicorn、Python、npm、端口等开发概念。

### 5. 设置落盘

以下配置应从环境变量迁移到设置页和本地配置：

- `MINIMAX_API_KEY`
- `MINIMAX_MODEL`
- Embedding provider/API Key
- 微信安装路径
- 工作时间
- 自动回复开关
- 安全词策略
- 开机自启

敏感字段保存时要脱敏展示，不在日志和错误提示中泄露。

### 6. 干净用户数据目录

正式 exe 不应把开发数据打进包。

需要把运行数据移动到用户目录，例如：

```text
%APPDATA%/WeChatAI/
  app/
  logs/
  memory/
  knowledge/
  users/
  identity/
  self_identity/
```

打包时必须排除：

- `wechat_ai/data/logs/`
- `wechat_ai/data/memory/`
- `wechat_ai/data/knowledge/uploads/`
- `wechat_ai/data/knowledge/local_knowledge_index.json`
- 测试聊天记录
- 真实用户身份
- 运行时 pid 文件

### 7. 知识库正式检索策略

当前知识库已支持文档入库、语义边界切片和检索，但正式回复质量仍取决于向量提供方。

第一版有两种选择：

- 接入真实 embedding，并在设置页完成配置。
- 暂时保留基础检索，但在 UI 中提示“当前知识库检索为基础模式”。

如果继续开启可信向量门禁，则必须保证小白能在设置页完成真实 embedding 配置，否则正式发送会被阻断。

### 8. 打包验收脚本

新增打包后验收流程：

- 干净环境首次启动。
- 启动本地服务。
- 后端健康检查。
- 微信环境检测。
- 导入 docx 知识库。
- 检索知识。
- 保存全局身份和客户身份。
- 启动自动回复。
- 运行 30 分钟真实微信冒烟。

## 建议删除或隐藏的内容

第一版 exe 不建议暴露：

- 安全策略审计。
- Debug prompt preview 页面入口。
- 知识库验收历史。
- 知识库可信门禁大块展示。
- Web 知识库构建入口。
- AI normalize preview/confirm 这类开发调试流程。
- 复杂日志管理、隐私策略、备份恢复入口。
- 英文内部状态码。
- trace_id、reply_xxx、draft_xxx 等内部 ID。
- 前端假数据、测试会话、测试客户、测试知识库内容。

后端接口可以暂时保留，前端入口先隐藏，避免第一版界面复杂。

## 建议开发顺序

1. 清理前端第一版功能边界，只保留用户真正需要的入口。
2. 建立用户数据目录，不再默认读写仓库内 `wechat_ai/data/`。
3. 完成 PyInstaller 后端 exe。
4. 完成 Electron 启动后端 exe 的服务管理。
5. 完成前端生产构建和 Electron 加载。
6. 接入设置页配置模型 Key、微信路径和 embedding。
7. 新增打包验收脚本。
8. 做干净机器首次启动测试。
9. 做 30 分钟真实微信冒烟测试。

## 当前进度判断

```text
后端核心能力：80%+
前端产品页：70% 左右
Electron 壳：50% 左右
exe 打包工程：20% 左右
小白一键使用体验：40% 左右
```

下一轮重点不是继续增加功能，而是围绕“启动、配置、数据、打包、验收”做产品化收口。
