# WeChatAuto 后续开发计划与收尾路线图

更新时间：2026-04-29

本文档用于统一旧计划、今日开发成果、剩余任务和验收标准。后续开发优先以本文档为主，历史设计文档只作为背景参考。

## 一、当前定位

项目已经从“能自动回复的脚本”推进到“有状态、有审核、有发送确认、有异常恢复的本地微信自动回复系统”。

当前更准确的阶段判断：

| 方向 | 当前完成度 | 说明 |
|---|---:|---|
| 自动回复主链路 | 约 80% | 普通低风险消息可以继续自动回复 |
| 消息去重和任务状态 | 约 85% | 已有消息、回复任务、发送任务、发送尝试记录 |
| 真实发送一致性 | 约 85% | 已接入发送前检查、发送锁、发送后确认 |
| 人工审核闭环 | 约 80% | 高风险消息可进入审核，批准后可进入发送流程 |
| 安全策略 | 约 75% | 已支持安全规则和规则组开关，配置体验仍需优化 |
| 发送异常处理 | 约 75% | 已支持发送不确定状态、暂停会话、人工恢复 |
| 知识库可信化 | 约 70% | 已有可信状态、验收历史、可信重建入口 |
| 前端管理台 | 约 70% | 核心入口可用，仍需体验和信息展示打磨 |
| 文档与交付 | 约 70% | 主要文档已更新，但需要进一步去重和统一 |

## 二、今日完成内容收敛

| 模块 | 今日完成内容 | 当前效果 |
|---|---|---|
| 任务状态底座 | 增强消息事件、回复任务、发送任务、发送尝试记录 | 关键链路可以追踪和恢复 |
| 发送协调 | 统一真实发送入口，增加发送锁、发送前检查、发送后确认 | 降低重复发送、错发和窗口被打断风险 |
| 发送不确定处理 | 明确发送不确定不会自动重发，并进入人工处理台 | 防止无法确认时重复发消息 |
| 人工审核 | 待审核页展示风险等级、原因码，批准后可继续发送 | 审核人员知道为什么拦截，也能完成发送闭环 |
| 安全策略 | 退款、价格、账号、验证码、提示词攻击等风险内容转人工 | 高风险消息不会直接自动发 |
| 自动回复误拦截修复 | 低风险普通消息不再因为知识库不可信而全部进审核 | 自动回复能力恢复，安全词仍然兜底 |
| 知识库可信化 | 增加可信状态、验收历史、可信重建入口 | 可以判断知识库是否适合支撑自动回复 |
| 启动和验收 | 统一启动脚本和桌面验收脚本可用 | 后续启动后能快速确认前后端是否正常 |
| 日志稳定性 | 日志读取跳过损坏行 | 避免一行坏日志导致前端日志页面报错 |

## 三、开发前后流程对比

| 流程 | 开发前 | 开发后 |
|---|---|---|
| 收到消息 | 直接生成回复，状态记录有限 | 先记录消息，再生成回复任务 |
| 普通消息 | 容易被过粗策略误拦截 | 默认继续自动回复 |
| 高风险消息 | 缺少统一规则 | 命中安全词后进入人工审核 |
| 人工审核 | 多数只是改状态 | 可批准、取消、转人工，批准后继续发送 |
| 真实发送 | 发送入口分散 | 统一进入发送协调流程 |
| 发送确认 | 不容易判断是否真的发出 | 区分已确认、失败、发送不确定 |
| 发送不确定 | 存在重复发送风险 | 不自动重发，等待人工处理 |
| 知识库可信度 | 不透明 | 前端可见可信状态和验收历史 |
| 排障 | 出错后主要看日志 | 有任务状态、日志、验收脚本共同定位 |

## 四、后续开发优先级

### 第一优先级：真实可用性收尾

目标：保证普通消息能稳定自动回复，风险消息才进入人工审核，发送异常可恢复。

| 任务 | 完成标准 | 验收方式 |
|---|---|---|
| 真实微信长时间运行验收 | 至少完成 30 分钟、2 小时、8 小时三档观察 | 按 `docs/p8-release-checklist.md` 记录结果 |
| 自动回复误拦截回归 | 低风险消息不进入待审核，高风险安全词进入待审核 | 后端建议接口和真实微信窗口双重验证 |
| 发送不确定处理复测 | 发送不确定不自动重发，会话暂停，人工确认后恢复 | 前端处理台和任务状态同时验证 |
| 启动脚本稳定性 | 一条脚本能拉起前端和后端，接口健康检查通过 | `scripts/dev_start.ps1 -Restart` |

### 第二优先级：人工审核和安全配置体验

目标：让非开发者也能理解和配置“哪些内容需要人工审核”。

| 任务 | 完成标准 | 验收方式 |
|---|---|---|
| 安全词配置页面优化 | 可直接增删安全词，不必手写完整配置 JSON | 设置页人工操作验证 |
| 风险原因中文化 | 待审核页显示中文原因，而不是只显示原因码 | 待审核页视觉检查 |
| 审核操作结果增强 | 批准并发送后能看到发送成功、失败、不确定 | Pending 页和发送任务列表检查 |
| 安全策略导入导出说明 | 文档说明如何备份和恢复安全策略 | 文档检查 |

### 第三优先级：知识库可信化增强

目标：让知识库不仅能检索，还能证明“为什么这样回复”。

| 任务 | 完成标准 | 验收方式 |
|---|---|---|
| 知识库证据接入审核页 | 人工审核时能看到命中的知识片段 | Pending 页检查 |
| 可信重建体验完善 | 重建前说明阻塞原因，重建后显示可信结果 | 知识库页检查 |
| 验收历史可读性优化 | 历史记录能看懂检索词、命中片段、可信状态 | 知识库页检查 |
| 低风险不拦截规则固化 | 知识库不可信只做提示，不默认拦截普通消息 | 单测和接口验证 |

### 第四优先级：运行时模块拆分

目标：降低后续维护成本，把过重的运行时主文件拆成清晰模块。

| 任务 | 完成标准 | 验收方式 |
|---|---|---|
| 消息扫描模块拆分 | 未读扫描、当前窗口监听边界清晰 | 单元测试通过 |
| 消息聚合模块拆分 | 多条消息合并、去重、顺序处理独立 | 回归测试通过 |
| 回复任务模块拆分 | 生成回复和创建回复任务逻辑独立 | 单元测试通过 |
| 发送协调模块收口 | 所有真实发送入口都只走统一协调流程 | 代码检索和发送测试 |

### 第五优先级：交付和产品化

目标：让项目可以被稳定启动、验收、交接。

| 任务 | 完成标准 | 验收方式 |
|---|---|---|
| 用户操作手册 | 写清启动、配置、安全词、审核、异常处理 | 文档检查 |
| 备份和迁移说明 | 写清本地数据、知识库、设置如何备份恢复 | 文档检查 |
| 发布清单统一 | 发布前只看一份清单即可完成验收 | `docs/p8-release-checklist.md` |
| 文档去重和归档 | 旧计划归档，新计划入口明确 | README 文档入口检查 |

## 五、下一轮可执行开发批次

下一轮开发建议从“真实可用性”和“人工可配置”开始，不再继续扩大架构范围。每一批都应独立可验收、可提交、可回滚。

### Round 21：安全词配置页面

目标：让人工可以直接维护“哪些词需要拦截”，不再要求用户手写完整安全策略配置。

| 内容 | 说明 |
|---|---|
| 主要改动 | 在设置页增加安全词管理区，按风险类型展示词库，支持新增、删除、启用、停用 |
| 涉及位置 | `desktop_app/frontend/app/settings/page.tsx`、`desktop_app/frontend/lib/api.ts`、`wechat_ai/app/settings_store.py`、`wechat_ai/safety/policy_engine.py` |
| 后端要求 | 保持现有安全策略结构兼容，新增词库保存后立即影响 `suggest_reply` 和真实自动回复 |
| 前端要求 | 普通用户能看懂“退款/价格/账号/验证码/提示词攻击”等分类 |
| 测试重点 | 修改安全词后，低风险消息继续自动回复，命中新增安全词的消息进入待审核 |
| 验收命令 | `py -3 scripts/test_wechat_ai_safety_unit.py`、`py -3 scripts/test_wechat_ai_app_service_unit.py`、前端构建检查 |

完成标准：

- 设置页可以直接维护安全词。
- 安全词改动会写入设置并留下审计记录。
- 不需要编辑 JSON 也能完成常见安全策略配置。

### Round 22：审核原因中文化和审核页增强

目标：让审核人员不用理解内部原因码，也能知道“这条消息为什么被拦截”。

| 内容 | 说明 |
|---|---|
| 主要改动 | 把风险等级、原因码、建议动作转成中文展示 |
| 涉及位置 | `desktop_app/frontend/app/pending/page.tsx`、`desktop_app/frontend/lib/api.ts`、`wechat_ai/server/core/catalog.py` |
| 后端要求 | 原因码保持稳定，必要时补充统一原因说明目录 |
| 前端要求 | 待审核卡片显示中文原因、风险等级、建议操作 |
| 测试重点 | 不同原因码都能显示为中文，不影响批准、取消、批准并发送 |
| 验收命令 | `npm run build`、`node desktop_app/frontend/tests/p5-frontend-acceptance.mjs` |

完成标准：

- 待审核页不再只显示 `reason_codes`。
- 人工能看到“命中价格类安全词”“疑似验证码/账号信息”“疑似提示词攻击”等中文说明。
- 审核动作后的发送结果仍然正常展示。

### Round 23：知识库证据接入审核页

目标：人工审核时能看到回复参考了哪些知识片段，避免只看一段草稿回复就做判断。

| 内容 | 说明 |
|---|---|
| 主要改动 | 待审核页展示知识库命中片段、可信状态、检索来源 |
| 涉及位置 | `wechat_ai/app/service.py`、`wechat_ai/runtime/knowledge_evidence.py`、`wechat_ai/server/schemas/desktop.py`、`desktop_app/frontend/app/pending/page.tsx` |
| 后端要求 | 回复任务中保留必要的知识证据摘要，避免写入过大原文 |
| 前端要求 | 审核卡片中展示“参考知识片段”和“知识库可信状态” |
| 测试重点 | 有知识命中时可见证据，无知识命中时不影响审核流程 |
| 验收命令 | `py -3 scripts/test_wechat_ai_app_service_unit.py`、`npm run build` |

完成标准：

- 人工审核时能看到回复依据。
- fake/untrusted 知识库只做提示，不默认拦截普通低风险消息。
- 高风险消息仍按安全策略进入审核。

### Round 24：真实微信冒烟和发送异常复测

目标：把“代码能过测试”推进到“真实微信窗口里能稳定跑一段时间”。

| 内容 | 说明 |
|---|---|
| 主要改动 | 完成 30 分钟真实微信冒烟，记录普通回复、高风险拦截、发送不确定处理 |
| 涉及位置 | `docs/p8-release-checklist.md`、`docs/p8-long-run-report-template.md`、`scripts/runtime_web_smoke_1min.ps1` |
| 后端要求 | 运行期间日志接口、任务状态接口不报错 |
| 前端要求 | Pending 页和首页状态能反映真实运行状态 |
| 测试重点 | 普通消息自动回复，高风险消息进入审核，发送不确定不重发 |
| 验收命令 | `powershell.exe -ExecutionPolicy Bypass -File scripts/dev_start.ps1 -Restart`、`py -3 scripts/run_desktop_acceptance_flow.py --base-url http://127.0.0.1:8765/api/v1 --skip-runtime-smoke --format pretty` |

完成标准：

- 30 分钟真实微信冒烟有记录。
- 没有重复发送、错发、无法停止、日志接口崩溃。
- 如果出现发送不确定，能在前端处理台完成恢复。

### Round 25：运行时拆分准备

目标：先明确拆分边界和测试保护，再开始移动运行时代码，避免大拆大改破坏自动回复。

| 内容 | 说明 |
|---|---|
| 主要改动 | 梳理扫描、聚合、回复任务、发送协调四个边界，补齐拆分前回归测试 |
| 涉及位置 | `wechat_ai/wechat_runtime.py`、`wechat_ai/runtime/message_flow.py`、`wechat_ai/runtime/send_coordinator.py`、`scripts/test_wechat_ai_unit.py` |
| 后端要求 | 拆分前后公开行为不变 |
| 前端要求 | 不新增页面功能，只保证接口行为不变 |
| 测试重点 | 未读聚合、群聊 sender、发送前检查、发送不确定、停止流程 |
| 验收命令 | `py -3 scripts/test_wechat_ai_unit.py`、`py -3 scripts/run_desktop_acceptance_flow.py --skip-http --skip-runtime-smoke --format pretty` |

完成标准：

- 形成明确拆分清单。
- 每个待拆模块都有对应回归测试。
- 不在这一轮做大规模迁移，只为后续安全拆分做准备。

### 推荐执行顺序

| 顺序 | 批次 | 原因 |
|---:|---|---|
| 1 | Round 21 安全词配置页面 | 直接解决人工可配置兜底问题 |
| 2 | Round 22 审核原因中文化 | 降低人工审核理解成本 |
| 3 | Round 23 知识库证据接入审核页 | 提升审核判断质量 |
| 4 | Round 24 真实微信冒烟和发送异常复测 | 验证前面改动是否真的可用 |
| 5 | Round 25 运行时拆分准备 | 最后再处理结构性重构，降低风险 |

## 六、统一验收标准

### 1. 代码和接口验收

```powershell
py -3 scripts\test_wechat_ai_unit.py
py -3 scripts\test_wechat_ai_app_service_unit.py
py -3 scripts\test_wechat_ai_safety_unit.py
py -3 scripts\run_desktop_acceptance_flow.py --base-url http://127.0.0.1:8765/api/v1 --skip-runtime-smoke --format pretty
```

### 2. 启动验收

```powershell
powershell.exe -ExecutionPolicy Bypass -File scripts\dev_start.ps1 -Restart
```

启动后检查：

| 检查项 | 地址 |
|---|---|
| 前端 | `http://127.0.0.1:3000` |
| 后端 | `http://127.0.0.1:8765/api/v1/ping` |
| 稳定性接口验收 | `py -3 scripts\run_stability_acceptance.py --base-url http://127.0.0.1:8765/api/v1 --format pretty` |

### 3. 真实微信人工验收

| 场景 | 期望结果 |
|---|---|
| 普通寒暄消息 | 自动生成并发送回复 |
| 包含退款、价格、账号、验证码等消息 | 进入人工审核 |
| 人工批准回复 | 进入发送协调流程，并记录发送结果 |
| 发送不确定 | 不自动重发，会话暂停，等待人工处理 |
| 停止自动回复 | 当前任务安全退出，不留下不可恢复状态 |

## 七、已知风险

| 风险 | 当前处理方式 | 后续动作 |
|---|---|---|
| 微信窗口焦点变化 | 发送锁和发送前检查降低风险 | 继续真实长跑验收 |
| 发送后确认不稳定 | 用已确认、失败、不确定三类状态区分 | 增强截图和证据展示 |
| 安全词误判 | 规则可配置，低风险默认放行 | 增加更友好的安全词管理页 |
| 知识库不可信 | 作为诊断提示，不默认拦截普通消息 | 完善可信重建和证据展示 |
| 文档分散 | 本文档作为统一路线图 | 后续逐步归档旧计划 |

## 八、当前推荐下一步

推荐先做三件事：

1. 先做 Round 21：安全词配置页面。
2. 再做 Round 22：审核原因中文化和审核页增强。
3. 然后做 Round 23：知识库证据接入审核页。

这三项完成后，再进入 Round 24 的真实微信 30 分钟冒烟；冒烟稳定后再推进 2 小时和 8 小时长跑，以及 Round 25 的运行时拆分准备。
